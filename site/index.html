Quick start

One handler. One source. One sink.

Summarize each article on a Kafka topic with an LLM and publish the summaries to another topic. The handler sees only the decoded value.

  • A transient API failure is retried with backoff.
  • Each offset is committed after its summary is published.
  • Ctrl-C drains in-flight work before the app exits.
src/main.rs 
use beavers::{
    App, Classify, Result, Utf8,
    adapters::kafka::{
        KafkaSink, KafkaSinkConfig,
        KafkaSource, KafkaSourceConfig,
    },
};

async fn summarize(article: String) -> Result<String> {
    let prompt = format!("Summarize: {article}");
    let summary = call_llm(&prompt).await.retry()?;
    Ok(summary)
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let articles = KafkaSource::<Utf8, _>::new(KafkaSourceConfig::new(
        "localhost:9092",
        "summarizer",
        ["articles"],
    ));
    let summaries = KafkaSink::<Utf8, _>::new(KafkaSinkConfig::new(
        "localhost:9092",
        "summaries",
    ));

    App::new()
        .subscribe("summarize", articles, summaries, summarize)
        .run()
        .await
}

How it fits together

An app runs many subscriptions side by side

Each subscription connects one source, one handler, and one sink. The app starts them together and shuts them down together.

Features

The plumbing you would otherwise write by hand

Typed handlers

Plain async functions from input to output. Codecs decode the payload before your code runs and encode the result after.

At-least-once delivery

An input is acknowledged only after its output is published. Nothing is committed on the way in.

Explicit failures

Classify each error as retry, reject, or fatal at the call site. Retries back off; rejects go to the dead-letter destination.

Concurrency with ordering

Bounded concurrency, per-key ordering, and a worker pool for blocking handlers.

Pipelines

Chain subscriptions through in-process channels. The upstream record is acknowledged when the last stage finishes.

Operations

Graceful shutdown, tracing spans, metrics, OpenTelemetry trace propagation, and /livez and /readyz probes.

Errors

Say what a failure means, where it happens

The runtime cannot tell a transient failure from a bad input. The handler can, so it decides with one call.

.retry()?
Run again under the retry policy, then dead-letter.
.reject()?
Dead-letter now. Plain ? does the same.
.fatal()?
Stop the subscription.
src/orders.rs 
use beavers::{Classify, Result};

async fn handle(order: Order) -> Result<Output> {
    // invalid input: dead-letter now
    validate(&order).reject()?;

    // transient: retry, then dead-letter
    let user = db
        .find_user(order.user_id)
        .await
        .retry()?;

    Ok(build_output(order, user))
}
